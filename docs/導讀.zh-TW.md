# squeeze264 導讀（給自己看的白話版）

這份文件的目的：讓你能在面試或專題展上，用自己的話把這個專案講清楚。
先看「一句話版本」，再看七個核心觀念，最後有檔案導覽和十個常見問題。

## 一句話版本

> 我照著 H.264 的官方規格書，從零寫了一個影片**編碼器**（把原始畫面壓成 .mp4），
> 壓出來的檔案 QuickTime 和 VLC 都能直接播；而且我用兩個別人寫的**解碼器**
> （ffmpeg 和 Apple 內建的 VideoToolbox）逐張畫面比對，證明它們解出來的每一個像素
> 都跟我的編碼器自己算的一模一樣。

這不是新發明。H.264 是 2003 年的國際標準，x264 這類成熟的編碼器早就存在。
這個專案的價值在於「照規格重做一遍，並且證明做對了」。

## 它解決什麼問題

一段 352×288、每秒 30 張的原始影片，10 秒鐘就有 45 MB。
壓成 H.264 之後大約 0.6 MB（約 70 分之一），肉眼看起來差不多。
編碼器的工作就是決定「哪些資訊可以不用存」和「剩下的怎麼存最省」。

## 七個核心觀念

### 1. 畫面切成 16×16 的小方塊（macroblock，巨集區塊）

整張畫面不會一次處理，而是切成一格一格 16×16 像素的方塊，一格一格壓。

**比喻**：拼圖。每一片拼圖各自決定要怎麼描述自己。

### 2. 預測：只存「跟猜的差多少」

對每個方塊，先「猜」它長什麼樣子，然後只存「實際畫面 − 猜的畫面」的差值（殘差）。猜得越準，差值越接近零，越好壓。

有兩種猜法：

- **畫面內預測（intra）**：用同一張畫面裡、左邊和上面已經處理過的像素往這邊延伸。
  有「垂直延伸」「水平延伸」「取平均」「斜向延伸」等模式（4×4 小塊有 9 種、16×16 有 4 種）。
- **畫面間預測（inter）**：到**上一張畫面**裡找一塊長得最像的，記下「往哪個方向移了多少」（**移動向量**）。

**比喻**：寫日記時不用每天重寫自我介紹，只寫「跟昨天一樣，但是換了一件外套」。

第一張畫面沒有「上一張」可以參考，只能全部用畫面內預測，這種畫面叫 **I 畫面**；
之後可以參考前一張的叫 **P 畫面**。如果某個方塊跟預測的幾乎完全一樣，就直接「跳過」（skip），幾乎不花位元。

### 3. 移動估計：在上一張畫面裡找最像的位置

「找最像的一塊」叫移動估計（motion estimation）。不可能每個位置都試，所以：

1. 先試幾個「很可能」的位置（鄰居方塊的移動向量、上一張同位置的向量、完全不動）。
2. 用六角形的圖案一步一步往「更像」的方向走，走到周圍都沒有更好的為止。
3. 再往「半個像素」「四分之一個像素」的位置微調。物體不會剛好移動整數個像素，所以規格定義了怎麼用
   6 個相鄰像素加權算出「像素之間」的值。

**比喻**：在地圖上找山頂。先從幾個有可能的地方出發，每次往比較高的方向走一步，最後在附近細細地找最高點。

### 4. 轉換與量化：把差值換成「頻率」，再丟掉細節

差值不直接存。先對每個 4×4 小塊做一個**整數轉換**（類似 JPEG 的 DCT），
把 16 個像素差值換成 16 個「頻率係數」：左上角代表整塊的平均，越往右下代表越細的紋理。

然後**量化**：把每個係數除以一個數再四捨五入。這是唯一會損失畫質的步驟。
除的數越大（QP 越高），越多係數變成 0，檔案越小、畫質越差。QP 每加 6，除數變兩倍。

**比喻**：量身高時只記到公分而不是公釐。記得越粗，要寫的數字越短，但也越不準。

### 5. 熵編碼（CAVLC）：常見的東西用短的代號

量化之後大部分係數是 0，剩下的多半是 ±1。CAVLC 用一組規格書裡定好的對照表，
把「有幾個非零係數、結尾有幾個 ±1、中間夾了幾個 0」這些資訊用長短不一的位元串表示，越常見的組合越短。
它還會看左邊和上面的小塊有多少係數，來選用哪一張表（因為鄰居通常很像）。

**比喻**：摩斯電碼。最常用的字母 E 只有一個點。

### 6. 編碼器裡面住著一個解碼器（這是整個專案最重要的觀念）

P 畫面是拿「上一張畫面」來猜的。但播放的人手上沒有原始的上一張，只有**解碼出來的**上一張（有量化誤差）。
所以編碼器不能拿原始畫面當參考，必須自己把剛壓好的東西再解回來，拿「解碼器會看到的畫面」當下一張的參考。

這代表：編碼器內部算出來的重建畫面，必須跟任何合格的解碼器算出來的**每一個像素都一樣**。
只要差一點點，兩邊的參考畫面就不同，誤差會一張一張累積，畫面越來越花。

**比喻**：兩個人各自照著同一份食譜做菜，然後下一道菜要拿上一道當材料。只要有一步不一樣，後面全部走樣。

這也是為什麼這個專案的測試重點是「跟真正的解碼器逐像素比對」。

### 7. 去方塊濾波：把格子邊緣的接縫磨平

每個小塊各壓各的，壓得兇的時候塊跟塊之間會出現明顯的接縫。H.264 規定解碼後要沿著每條 4×4 的邊做平滑處理，
而且濾波後的畫面才是下一張的參考（所以叫「迴路內」濾波）。濾波的強度看兩邊是怎麼壓的、QP 多高、
邊緣兩側差多少（差太多代表那是真的物體邊緣，不能磨掉）。

**比喻**：貼磁磚之後補縫。縫太明顯就補，但是磁磚本身的花紋不能抹掉。

## 檔案導覽（每個檔案在做什麼）

| 檔案 | 用途 |
|---|---|
| `src/main.rs` | 命令列程式：`encode`（壓縮）、`check`（壓完找解碼器比對）、`gen`（產生合成測試影片）。 |
| `src/encoder.rs` | 一張畫面的流程：決定是 I 還是 P、叫每個方塊去壓、濾波、更新參考畫面、統計。 |
| `src/analysis.rs` | 做決定：這個方塊要跳過、用畫面間、還是畫面內？切成幾塊？也包含「亂數做決定」的測試模式。 |
| `src/mb.rs` | 照決定去做：算預測、算差值、轉換量化、重建、把語法寫進位元流。 |
| `src/me.rs` | 移動估計（六角形搜尋＋次像素微調）。 |
| `src/mvpred.rs` | 移動向量的預測（只存「跟鄰居猜的差多少」）。 |
| `src/inter.rs` | 畫面間預測的取樣：半像素、四分之一像素內插。 |
| `src/intra.rs` | 畫面內預測的各種模式。 |
| `src/transform.rs` | 4×4 整數轉換、量化、反量化、反轉換。 |
| `src/cavlc.rs` | 係數的熵編碼。 |
| `src/tables.rs` | 從規格書抄來的各種表（CAVLC 代碼、量化表、濾波門檻、level 限制）。 |
| `src/deblock.rs` | 去方塊濾波。 |
| `src/headers.rs` | 檔頭：SPS、PPS、slice header（告訴解碼器畫面多大、用了哪些功能）。 |
| `src/bitstream.rs` | 一個位元一個位元地寫、Exp-Golomb 編碼、NAL 單元包裝。 |
| `src/mp4.rs` | 自己寫的 MP4 封裝，讓 QuickTime 能直接打開。 |
| `src/ratecontrol.rs` | 位元率控制：固定 QP，或自動調 QP 讓平均位元率接近目標。 |
| `src/verify.rs` | 呼叫 ffmpeg 解碼並逐張比對。 |
| `tests/conformance.rs` | 最重要的測試：各種設定、亂數決定、真實影片，全部要跟解碼器完全一致。 |
| `tools/bench.py` | 跟 x264 比壓縮效率。 |
| `tools/report.py` | 產生網頁報告。 |
| `tools/mutants.py` | 故意在程式裡放一行錯，確認測試抓得到。 |
| `跑跑看.command` | 雙擊就能跑完整流程。 |

## 十個常見面試問題

**1. 你怎麼知道你的編碼器是對的？**
編碼器內部本來就會算出「解碼後的畫面」。我把壓出來的檔案交給 ffmpeg 和 Apple VideoToolbox 兩個獨立的解碼器，
要求它們輸出的每一張畫面跟我算的位元組完全相同，而且解碼器不能印出任何警告。
另外有亂數測試：讓編碼器隨機選各種模式、切法、移動向量，一樣要完全一致。
我還故意在程式裡放了二十幾個一行的錯誤，確認測試每一個都抓得到。

**2. 跟 x264 比起來怎麼樣？**
把 x264 限制成跟我一樣的功能（Baseline、單一參考畫面、不做 RD 最佳化）時，兩者差不多（−4% 到 +2%）。
x264 打開它在 Baseline 下的 RD 最佳化之後，我多用 0–21% 的位元。跟 x264 預設值（High profile，
有 CABAC、B 畫面、8×8 轉換）比，我要多用 70–115% 的位元。速度上 x264 快大約十倍，因為它有手寫的組合語言。
實際數字在 README 和 `docs/results.html`。

**3. 為什麼編碼器要包含解碼器？**
因為預測要用「解碼器手上會有的畫面」，不是原始畫面。見上面第 6 點。

**4. I 畫面和 P 畫面差在哪？**
I 畫面只用自己畫面內的資訊，可以獨立解碼，但比較大。P 畫面會參考前一張，小很多，但要先有前一張才解得開。
所以每隔一段（預設 250 張）放一張 I 畫面，讓播放器可以從那裡開始播或快轉。

**5. QP 是什麼？**
量化參數，0 到 51。越大量化越粗、檔案越小、畫質越差。每加 6，量化步階變兩倍，位元率大約減半。

**6. 移動向量為什麼要到四分之一像素？**
真實的物體移動不會剛好是整數像素。能表示到 1/4 像素，預測會準很多，差值更小。
代價是要用濾波器算出像素之間的值，而且這個濾波器的算法必須跟規格完全一致。

**7. 最難的部分是什麼？**
不是哪個演算法，而是「每一個細節都要跟規格一模一樣」：五百多個 CAVLC 代碼、
某個鄰居算不算「可用」、四捨五入是加 16 還是加 15。錯一個位元，解碼器就會解出不同的畫面。
我的作法是每個部分都對照規格的公式寫單元測試，再用真正的解碼器當最後的裁判。

**8. 有什麼沒做？**
CABAC、B 畫面、8×8 轉換、多張參考畫面、交錯式掃描、多執行緒、SIMD。這些是 x264 比我好的主要原因。
另外固定 QP 模式下不保證位元率在 level 的上限以內。

**9. 為什麼用 Rust？為什麼不用現成的函式庫？**
Rust 沒有垃圾回收、速度接近 C，而且陣列越界會被抓到，寫這種大量操作陣列索引的程式比較安心。
整個編碼器沒有用任何第三方套件，因為專案的目的就是自己把每個部分做出來。ffmpeg 只用來當「裁判」，是另外執行的程式，沒有連結進來。

**10. 如果一個方塊壓完反而比原始資料還大怎麼辦？**
規格規定一個方塊最多 3200 位元。雜訊畫面在 QP 很低的時候會超過，這時編碼器會退回去，
改用 I_PCM 模式直接存原始像素（3072 位元）。這個情況有專門的測試。

## 可以現場示範的指令

```sh
make build                 # 編譯
make test                  # 所有測試（含跟 ffmpeg 逐像素比對）
./target/release/squeeze264 check data/foreman_cif.y4m --qp 28   # 壓縮＋四種解碼驗證
./跑跑看.command            # 完整流程，最後打開影片和報告
```
